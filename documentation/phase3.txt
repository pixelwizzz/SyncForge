========================================================================
             SYNCFORGE PROJECT DOCUMENTATION - PHASE 3
                Task Management & Team Collaboration
========================================================================

------------------------------------------------------------------------
1. OVERVIEW: WHAT IS PHASE 3?
------------------------------------------------------------------------
Phase 3 is the core "Domain Logic" of SyncForge. It establishes the actual 
business value of the application: collaboration teams, team memberships 
with custom roles (Owner, Admin, Member), full CRUD (Create, Read, Update, 
Delete) capabilities for tasks, input validation layers, and development 
database seeding.

------------------------------------------------------------------------
2. WHY DID WE DO THIS? (Architectural & Business Rationale)
------------------------------------------------------------------------
In your project defense, you should explain the design decisions like this:
* Team-Scoped Collaboration: Tasks cannot exist in a vacuum. To scale a 
  collaborative task manager, every task must belong to a "Team". This 
  creates a clean sandbox environment for different workgroups.
* Role-Based Access Control (RBAC): We must prevent regular team members 
  from deleting whole teams, and block external users from modifying 
  confidential tasks. Access is enforced based on team membership.
* Validation at the Gate: Standardizing inputs prevents bad data from 
  polluting our database or crashing our node services.
* Database Syncing over Manual SQL: We leveraged Sequelize's native 
  auto-sync system (`alter: true`) to construct our tables automatically 
  on boot, saving days of writing complex raw SQL constraints.

------------------------------------------------------------------------
3. HOW DID WE DO IT? (Technical Implementation Details)
------------------------------------------------------------------------
We designed and implemented this logic across several key systems:

A. Centralized Model Associations (`src/models/associations.js`)
   Sequelize models are decoupled, but database tables are highly relational. 
   We created a single central associations file to wire them together:
   * Users can belong to many Teams through TeamMembers (Many-to-Many).
   * Teams have many Tasks (One-to-Many).
   * Users create tasks (Creator) and are assigned tasks (Assignee).
   * Tasks have many Attachments.

B. Generic Validation Middleware (`src/middleware/validate.js`)
   We built a reusable controller decorator using `Zod` schemas. If a request 
   fails schema verification (e.g. team name is too short, email is invalid), 
   the middleware immediately intercepts the request and returns a structured 
   400 Validation Error before hitting our database.

C. Team Management Engine (`src/teams/`)
   * Models & Services: Tracks teams and roles (`owner`, `admin`, `member`). 
     When a user creates a team, they are automatically bound as the `owner`.
   * Endpoints: Includes `/teams` (listing your teams), `/teams/:id` 
     (viewing a specific team with its members), and `/teams/:id/invite` 
     (adding a registered email to a team with a specific role).

D. Task Management Engine (`src/tasks/`)
   * Models & Services: Handles task title, description, status (`todo`, 
     `in_progress`, `done`), priority (`low`, `medium`, `high`), and assignees.
   * Paginated Queries: Implemented offset pagination on `/tasks` so a frontend 
     only fetches what it needs (e.g., 10 tasks at a time), keeping queries extremely fast.
   * RBAC Security: Enforces that only the creator, team owner, or team admin 
     can delete a task.

E. Mock Data Seeder (`src/utils/seed.js`)
   We built an automated seeder that drops all existing tables and re-seeds 
   the system with 4 mock users (Alice, Bob, Charlie, Diana), two teams 
   ("Engineering Team", "Creative Studio"), and 5 realistic tasks. 
   This makes local postman testing instant and repeatable!

------------------------------------------------------------------------
4. WHAT CHANGES DOES THIS CREATE IN THE APPLICATION?
------------------------------------------------------------------------
* High-Performance Relational Schema: PostgreSQL now manages 5 connected tables 
  with foreign keys: `users`, `teams`, `team_members`, `tasks`, `attachments`.
* Endpoint Expansion: The server now supports:
  - `POST /api/v1/teams` (Create team)
  - `GET /api/v1/teams` (Get user's teams)
  - `GET /api/v1/teams/:id` (Get team details + members)
  - `POST /api/v1/teams/:id/invite` (Invite members)
  - `POST /api/v1/tasks` (Create task)
  - `GET /api/v1/tasks` (List & query tasks)
  - `PUT /api/v1/tasks/:id` (Update status/assignee)
  - `DELETE /api/v1/tasks/:id` (Delete task)

------------------------------------------------------------------------
5. WHY IS THIS IMPORTANT FOR THE PROJECT?
------------------------------------------------------------------------
Phase 3 represents the core offering of SyncForge. It proves that:
1. You can design standard database relationships (foreign keys, cascading 
   deletes, unique multi-column indexes).
2. You can secure endpoints using flexible, reusable RBAC middlewares.
3. You write production-grade, highly validated endpoints that catch input 
   errors instantly.
4. You write clean, scalable service-layer architectures separating business 
   logic from routing.
