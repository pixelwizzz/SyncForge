========================================================================
             SYNCFORGE PROJECT DOCUMENTATION - PHASE 2
             Clerk Authentication & User Synchronization
========================================================================

------------------------------------------------------------------------
1. OVERVIEW: WHAT IS PHASE 2?
------------------------------------------------------------------------
Phase 2 focuses entirely on Authentication (verifying WHO a user is) 
and Authorization (verifying WHAT a user is allowed to do). Instead of 
building a custom login system from scratch, we integrated "Clerk," an 
enterprise-grade external authentication provider, and synchronized it 
with our local PostgreSQL database.

------------------------------------------------------------------------
2. WHY DID WE DO THIS? (The Architectural Decision)
------------------------------------------------------------------------
In a project defense or interview, you might be asked: "Why didn't you 
just use bcrypt and JWT to build your own login system?"

Here is the answer:
* Security Risks: Handling passwords locally is extremely dangerous. A 
  single bug in cryptography or a database leak could expose user passwords.
* Maintenance: Building password reset flows, email verification, OAuth 
  (Google/GitHub login), and session rotation takes weeks and requires 
  constant security updates.
* The Modern Standard: Modern web architecture uses Identity as a Service 
  (IDaaS). By using Clerk, we offload the highest-risk component of our 
  app to security experts. Our backend remains lightweight, fast, and 
  100% focused on business logic (tasks and teams), not password math.

------------------------------------------------------------------------
3. HOW DID WE DO IT? (The Implementation Details)
------------------------------------------------------------------------
We implemented this integration using five main components:

A. The Database User Model (`src/users/user.model.js`)
   Instead of storing a "password_hash", our local database only stores 
   a `clerk_id`, `email`, `name`, and an `is_admin` flag. We rely on 
   Clerk's ID to uniquely identify the user.

B. The Webhook Receiver (`src/webhooks/clerk.webhook.js`)
   When a user signs up on the frontend using Clerk, Clerk's servers 
   send a real-time HTTP POST request (a webhook) to our server. We use 
   a library called `svix` to cryptographically verify the signature of 
   this request to ensure hackers aren't faking signups. Once verified, 
   our server automatically creates the user in our local PostgreSQL database.

   *Developer Feature*: We built a "Dev Bypass" so if you run the app 
   locally without a webhook secret, it bypasses the strict signature 
   check, making local testing with Postman incredibly easy.

C. The Authentication Guard (`src/middleware/authenticate.js`)
   Whenever a user requests private data (like their tasks), they send a 
   Session JWT (provided by Clerk) in their request. Our middleware uses 
   Clerk's official SDK to verify this JWT, extracts the user's `clerk_id`, 
   looks up their full profile in our database, and attaches it to the 
   request as `req.dbUser`.

D. The Authorization Guard (`src/middleware/authorize.js`)
   Authentication is proving WHO you are. Authorization is proving WHAT 
   you can do. We built middleware that checks if `req.dbUser.is_admin` 
   is true before allowing access to global settings. We also built the 
   foundation for Team-Role checks (Owner, Admin, Member) which will be 
   used in Phase 3.

E. The Profile Endpoint (`src/auth/auth.controller.js`)
   We built `GET /api/v1/auth/me`. This simple endpoint allows the 
   frontend application to easily ask our backend for the active user's 
   local database profile.

------------------------------------------------------------------------
4. WHAT CHANGES DOES THIS CREATE IN THE APPLICATION?
------------------------------------------------------------------------
* Stateless Backend: Our backend no longer stores "sessions" in memory. 
  Every request must carry a valid Clerk JWT, making our server highly 
  scalable.
* Zero Password Endpoints: We no longer have `/register`, `/login`, 
  or `/forgot-password` endpoints. The frontend talks directly to Clerk 
  for these actions.
* Automated Data Sync: Our local database is a "follower" of Clerk. If a 
  user updates their profile picture on Clerk, the webhook fires, and our 
  database updates automatically.

------------------------------------------------------------------------
5. WHY IS THIS IMPORTANT FOR THE PROJECT?
------------------------------------------------------------------------
If you are presenting this project, highlighting this architecture shows 
immense maturity. It demonstrates that you understand:
1. Microservice integration (connecting our server to Clerk's servers).
2. Cryptographic security (using `svix` for webhook signatures).
3. Database design (separating auth data from business data).
4. Middleware concepts (creating an elegant pipeline to guard routes).

This phase transformed our application from an unprotected sandbox into a 
secure, production-ready backend capable of handling real users safely.
